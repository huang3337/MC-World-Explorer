### ISSUE-USEWORLD-001：固定 1024×1024 表面成为首屏阻塞门槛，随后又被瓦片链路重复计算

- **严重程度**：🟠 高
- **类别**：资源管理 / 模块耦合 / UI 健壮性
- **文件**：`src/composables/useWorldExplorer.ts`、`src/App.vue`
- **行号**：`useWorldExplorer.ts:163-205`、`App.vue:24-28,76`
- **状态**：待修复

**问题描述**：
选择世界后必须先等待 `loadSurface` 完整生成 1024×1024 方块固定表面，`MapViewport` 才会挂载；组件挂载后又立即通过 `load_map_tile` 请求当前视口瓦片。两条链路覆盖相同世界区域，却没有共享区块解码或表面采样结果。

**当前代码**（审查时快照）：

```ts
operation.value = "surface";
phase.value = "surface-loading";
const nextSurface = await backend.loadSurface(selected.sessionId);
// ...
surface.value = nextSurface;
```

```vue
<MapViewport v-if="surface" :data="surface" ... />
```

**问题分析**：
当前 1024×1024 固定表面最多相交 65×65 个区块。该任务完整结束以前，用户看不到可交互地图；任务结束后，`MapViewport.reset()` 仅把这份结果制作成临时底图，同时再次调度当前视口瓦片。后续瓦片由另一条核心路径重新打开 Region、解压 NBT、解码 section 并逐列采样，因此首屏等待成本没有转化为可复用的瓦片结果，且同一区域发生重复 CPU 与磁盘读取。Java 版地图直接围绕瓦片服务组织首屏，不存在“先完成一张固定大图，才能启动瓦片地图”的串联门槛。

这解释了用户观察到的“进入二维预览本身很慢”：延迟不仅来自瓦片加载，还包含此前不可见的固定表面全量计算。现有单元测试使用模拟后端验证状态切换，没有覆盖真实存档下固定表面与瓦片重复工作的耗时和读取次数。

**建议修改**：
本轮按开发者要求仅记录问题分析，暂不提出解决方案；等待后续专门的二维加载方案评审。

**影响范围**：
真实世界首次打开时间、世界切换等待时间、初次可交互时间，以及随后当前中心区域的重复计算量。
