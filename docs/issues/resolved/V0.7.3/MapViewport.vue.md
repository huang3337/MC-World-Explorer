### ISSUE-MAPVIEWPORT-001：可见瓦片通过串行 await 瀑布加载，且整块完成前没有局部结果

- **严重程度**：🟠 高
- **类别**：资源管理 / UI 健壮性
- **文件**：`src/components/MapViewport.vue`
- **行号**：`68-79,103-105`
- **状态**：待修复

**问题描述**：
`loadVisible()` 对可见瓦片执行 `for` 循环，并在循环内部逐个 `await loadMapTile()`；下一块必须等待上一块完成。单个 256×256 像素瓦片只有在后端完成全部区块读取、采样、着色、编码及前端解码后才加入画布。

**当前代码**（审查时快照）：

```ts
for (const target of targets) {
  // ...
  const data = await loadMapTile(
    props.data.metadata.sessionId,
    target.tileX,
    target.tileZ,
    target.blocksPerPixel,
  );
  // 完整响应返回后才创建图像并 draw()
}
```

**问题分析**：
瓦片边长固定为 `256 × blocksPerPixel` 方块，因此单块在 1、2、4、8、16 方块/像素下分别覆盖 256、1,024、4,096、16,384、65,536 个区块槽位。视口通常同时需要多块瓦片，串行等待使总完成时间接近各瓦片耗时之和；缩小地图时单块工作量还会平方增长。

Java 版 `MapTileScheduler` 同时使用两个有界 worker，并按距视口中心的优先级提交全部可见瓦片；`MapTileGenerator` 还以约 100 ms 间隔发布局部图像，最终瓦片未完成时也能逐步出现。Tauri 版虽按中心距离排序目标，但排序后仍逐个等待，也没有局部传输/提交路径。因此用户看到的是长时间空白或固定底图，而不是逐块、逐区域补全，感知速度与 Java 版存在结构性差距。

当前没有 `MapViewport.vue` 组件测试；`mapViewportMath.test.ts` 只验证坐标数学，未覆盖多瓦片调度顺序、首块显示时间或交互期间的请求废弃。

**建议修改**：
本轮按开发者要求仅记录问题分析，暂不提出解决方案；等待后续专门的二维加载方案评审。

**影响范围**：
首次显示、拖动、缩放、定位后的瓦片补全速度，以及大视口和低倍率下的可用性。

### ISSUE-MAPVIEWPORT-002：当前“完整加载”只表示请求结束，不能表示存档已加载区块完整可见

- **严重程度**：🟠 高
- **类别**：错误处理 / UI 健壮性
- **文件**：`src/components/MapViewport.vue`、`src/composables/mapViewportMath.ts`
- **行号**：`MapViewport.vue:19,42-55,68-79,101-115`、`mapViewportMath.ts:19-31`
- **状态**：待修复

**问题描述**：
当前只计算当前视口相交的瓦片，不枚举存档 Region 范围，也不预取相邻瓦片；同时未加载区域、缺失区块和整块请求失败均可能呈现为相同或近似的深色背景。`loading` 降为零以后，界面固定显示“当前视口瓦片已加载”，即使其中有请求失败或没有瓦片被提交。

**当前代码**（审查时快照）：

```ts
const targets = visibleTiles(view.value, width, height, committedZoom.value);
// ...
catch (reason) {
  if (!isCancellation(reason)) loadError.value = reason as DisplayError;
} finally {
  loading.value = Math.max(0, loading.value - 1);
}
```

```vue
<span role="status">
  {{ loading ? `正在加载 ${loading} 个地图瓦片…` : "当前视口瓦片已加载" }}
</span>
```

**问题分析**：
`visibleTiles()` 的输入只有视口中心、视口尺寸和倍率，所以系统不知道存档已有区块的整体边界，也没有“全存档已发现区块集合”可用于完整度判断。对用户指定的“雪山”真实存档进行只读 Region 头统计，主世界包含 152 个 Region 文件、82,085 个已占用区块槽位，Region 坐标粗范围为 X `-7..7`、Z `-11..5`，总大小约 819.55 MiB。当前首次固定底图只覆盖 1024×1024 方块，之后只补当前视口瓦片；它不具备一次生成上述全部已存在区块预览的流程。

Java 版同样不是一次性生成整个无限世界，但它明确区分目标、就绪、局部、失败和重试状态，并对视口外围做预取；因此连续浏览时更接近“已加载区块可随视口完整出现”。Tauri 版只有一个 `loadError` 和剩余请求计数：失败目标不会进入 `tiles`，计数却仍归零；画布底色 `#20262b` 又与缺失状态色相同，导致“尚未加载”“区块不存在”“整块请求失败”无法可靠区分。64 项 Map 采用插入顺序淘汰，命中不会提升热度，不同倍率的旧瓦片共同占用容量；回看和缩放会进一步制造视觉空缺及重复加载。

因此用户报告的“不完整”至少包含两层：当前范围设计未覆盖存档全部已存在区块；在已经请求的当前视口内，界面也无法准确证明全部目标成功提交。仅凭当前“已加载”文字不能认定数据完整。

**建议修改**：
本轮按开发者要求仅记录问题分析，暂不提出解决方案；等待后续专门的完整度语义与加载范围评审。

**影响范围**：
大世界总览、连续拖动和缩放、返回已浏览区域、失败诊断、用户对地图完整度的判断，以及后续对齐 Java 版的验收标准。

## 2026-09-26 ISSUE-MAPVIEWPORT-002 显示倍率与目标集合补充

- **发现的问题**：当显示倍率小于瓦片数据倍率时，前端按实际显示范围核对目标，后端却按数据倍率扩大视口范围。两端可能得到不同的目标集合，把正常摘要误判为 `INVALID_RESPONSE`；连续缩放后的定位或拖动会触发该路径。
