### ISSUE-EXECUTOR-004：单活动任务加单 pending 的全局槽位无法承载多瓦片地图调度

- **严重程度**：🟠 高
- **类别**：资源管理 / 模块耦合
- **文件**：`src-tauri/src/tasks/executor.rs`、`src-tauri/src/commands/load_map_tile.rs`
- **行号**：`executor.rs:32-39,91-155,227-266`、`load_map_tile.rs:30-37`
- **状态**：待修复

**问题描述**：
每个 `load_map_tile` 都提交到同一个应用级执行器。该执行器只有一个物理 worker、一个 active 和一个 latest pending；新提交会替换已有 pending，并通过共享任务登记器使旧任务结果过期。

**当前代码**（审查时快照）：

```rust
struct ExecutorState {
    registry: TaskRegistry,
    active: Option<TaskHandle>,
    pending: Option<Job>,
    // ...
}

let replaced = state.pending.replace(Job { /* ... */ });
```

**问题分析**：
当前前端逐个等待瓦片，因此所有工作实际按单 worker 串行完成；如果前端同时提交多个可见瓦片，执行器又只保留最新 pending，并使前序任务过期，不能直接获得 Java 版“两个有界 worker、全部可见瓦片按优先级排队”的吞吐和稳定提交语义。二维瓦片还与固定表面、三维网格、世界选择共享同一槽位，长瓦片会占据唯一重型执行边界。

该行为符合 DECISION-022 在最小垂直切片阶段确定的单槽模型，但 DECISION-028 后二维范围和交互已经扩大，执行模型仍停留在旧容量假设。因而它是当前串行延迟的后端结构性约束，也会让任何多瓦片并发或预取尝试发生相互取消。现有执行器测试明确证明峰值并发为 1 且三个请求只保留最新 pending；测试验证的是旧契约本身，没有验证该契约是否仍满足二维 Java 对等目标。

**建议修改**：
本轮按开发者要求仅记录问题分析，暂不提出解决方案；等待后续专门的任务隔离与吞吐方案评审。

**影响范围**：
二维瓦片首屏、拖动、缩放、未来预取与并行调度，并可能影响二维和三维任务之间的响应性。

## 2026-09-26 实施复核

- **当前结论**：原审查中的“全局单 active、单 pending、单 worker 承载正式二维多瓦片”的结构性问题，已由 DECISION-023 确认的独立地图调度域替换。正式 `start_map_viewport` 使用固定 2 个地图 worker、96 项等待队列、可见中心优先和外围预取；原单 worker 执行器仍承载非地图重任务及保留的兼容 `load_map_tile` 命令，不再承载正式二维视口。上方原始审查快照保留不变。
- **本次补强**：复核发现视口切换瞬间仍可能有旧 worker 持有旧身份并迟到入队，也可能有旧长轮询取走新视口结果。结果队列现以当前会话/视口任务身份限制入队，旧局部结果只丢弃而不使已重新绑定的工作误报失败，旧终态不得入队；长轮询在队列锁内核对视口身份，过期请求不能消费新任务结果。精确取消后，迟到结果同样被拒绝。未更改 worker 数量、队列容量或通用执行器契约。
- **自动化证据**：调度器测试覆盖同时 2 个 worker、额外任务排队、优先级与稳定顺序、96 项上限、相同任务重绑定、取消后重新排队、worker panic 隔离和关闭；新增切换/取消后迟到局部及终态拒绝测试，以及旧长轮询不得消费新结果的确定性测试。2026-09-26 定向任务域 41 项、Rust fmt、Clippy、workspace tests、TypeScript typecheck 与前端 126 项 Vitest 均通过；真实存档与真实关闭负载未执行。
- **验收缺口**：仍须经单独批准验证真实多瓦片负载下的吞吐、拖动/切换任务、队列压力、旧结果拒绝和资源释放，才能将本 Issue 标记已修复。5 秒关闭等待预算单列于 ISSUE-TAURILIB-004，不由本项合成测试代替。

## 2026-09-26 运行中预取保留补充

- **发现的问题**：固定加载中心的后台预取若仍在等待队列，视口移动后可保留；但同一瓦片已被 worker 取出执行时，即使仍属于新视口的后台集合，也会被取消，导致进行中的预取无谓重做。
- **实际修改**：新视口继续包含该后台目标、任务尚未取消或完成且从未作为可见结果发布时，运行中的预取重新绑定到新视口并继续保持后台身份。已移出后台集合的任务仍取消；可见目标仍优先，worker 数和队列容量不变。
- **自动化证据**：新增确定性测试，修复前复现运行中预取被取消且停留在旧任务 ID；修复后验证继续执行、不发布可见结果，并以对照测试验证移出后台集合时仍取消。地图调度器 16 项测试、Rust fmt 与 workspace Clippy 通过。真实存档和关闭负载未执行，本 Issue 保持活动状态。

## 2026-09-26 世界切换任务收束补充

- **发现的问题**：成功切换世界只取消通用执行器，旧地图 worker 和长轮询不随会话提交收束；旧视口启动与世界提交交错时，还可能在取消后登记旧轮询状态。
- **实际修改**：候选世界验证失败时保留现有视口；成功提交新会话后，按旧会话与视口任务身份精确取消地图任务、丢弃结果并唤醒轮询。视口创建、登记和可见任务提交与会话提交互斥，过期会话不得重新占用调度域；不改变双 worker、容量和关闭预算。
- **自动化证据**：合成世界回归测试先复现旧长轮询未过期，再验证失败候选不影响现有视口、成功切换取消旧 worker 与轮询、过期启动被拒绝且新视口可用。世界选择测试 5 项、视口命令测试 5 项通过；调度器 16 项复跑通过，其中一项基于双 worker 完成顺序的断言曾偶发失败，需在统一测试阶段单独消除测试时序依赖。真实存档和关闭负载未执行，本 Issue 保持活动状态。

## 2026-09-27 ISSUE-EXECUTOR-004 解决与归档

- **解决状态**：已修复并归档。上方原始审查快照及实施过程中的“保持活动”表述保留为当时记录；本节为最终结论。
- **解决日期**：2026-09-27。
- **实际修改**：正式二维视口已从通用单 worker、单 pending 执行器迁入独立的固定双 worker、有界等待队列地图调度域，支持可见中心优先、外围预取、同瓦片重绑定及协作取消。世界切换、视口替换和关闭按会话/任务身份收束工作并拒绝迟到结果；兼容 `load_map_tile` 命令仍沿用通用执行器，不是正式二维视口路径。
- **自动化证据**：调度器测试覆盖双 worker 并行、排队顺序与容量、重绑定、取消、预取保留及关闭；结果队列和轮询测试覆盖旧会话、旧视口与迟到结果隔离，世界切换测试覆盖旧任务收束和新视口可用。2026-09-27 Rust workspace tests、fmt、Clippy、TypeScript typecheck 和前端 144 项 Vitest 均通过；默认忽略的真实存档集成测试不计入本次自动化通过项。
- **人工验收**：开发者在此前获批的真实存档桌面测试中观察到可见瓦片最多同时加载两个，拖动、世界切换和关闭没有任务卡住，关闭过程可正常快速结束；开发者确认不同数据倍率生成各自瓦片的加载现象符合当前行为，并批准本 Issue 收口。本次未重新读取真实存档，也未取得吞吐时间或跨世界热缓存的 Java 对照数据。
- **范围边界**：收口的是正式二维多瓦片调度不再受全局单槽替换的问题，不表示各数据倍率首次加载免计算，也不表示跨世界/跨启动热缓存或整体加载速度已与 Java 对等；后者仍依当前路线在 V0.7.4 验证。
