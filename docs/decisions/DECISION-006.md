# DECISION-006：V0.3.1 采用显式局部恢复与分阶段发布门槛

- **状态**：已确认
- **确认日期**：2026-07-30
- **确认人**：项目开发者
- **适用版本**：V0.3.1

## 决策背景

V0.3 已完成主要地图浏览功能，但软件包发布前仍需要完善地图块失败恢复、多人玩家标记识别、缓存清理反馈和整体发布验收。

这些选择会影响地图加载状态管理、视口交互、缓存维护接口、测试范围、版本提交时点和最终发布流程，因此作为重大开发决策记录。

## 备选方案

### 地图块失败恢复

1. 只在状态栏提示失败，由用户清理整个存档缓存。
2. 增加独立的全局“重试”按钮。
3. 对失败地图块持续自动重试。
4. 首次失败自动重试一次，持续失败后点击对应地图块单独重试。

### 玩家定位反馈

1. 玩家标记永久显示名称。
2. 只在悬停时显示身份信息，列表定位后短时高亮目标。
3. 增加标记聚合和自动避让系统。

### 缓存维护

1. 保持现有无容量信息的清理按钮。
2. 清理前统计当前存档缓存，清理后报告实际释放量并重新加载当前视口。
3. 增加自动过期、容量上限和后台淘汰。

### 发布流程

1. V0.3.1 功能完成后立即提交并发布。
2. 每完成一个功能创建阶段性提交。
3. 所有变更保留在工作区，通过完整验收和人工确认后统一提交，再从确定提交构建最终软件包。

## 最终选择

- 每个地图块首次失败后自动重试一次。
- 第二次失败后显示明确失败覆盖层，用户点击该地图块即可只重试该块。
- 不增加独立重试按钮，不把缓存清理作为失败块重试入口，不允许无限自动重试。
- 玩家标记仅在悬停时显示名称、维度和坐标。
- 点击玩家列表后按既有规则定位，并将目标玩家标记高亮约 3 秒。
- 不增加永久名称、标记聚合或自动避让。
- 现有缓存按钮改名为“清理存档缓存并重新加载”。
- 沿用现有清理后刷新当前视口的行为，保留维度、显示层、中心和缩放。
- 清理前显示当前存档缓存文件数量和容量，清理后显示实际释放量。
- 不增加自动缓存淘汰或自动清理。
- V0.3.1 必须通过完整自动化、真实多维度和多人存档、30 分钟交互压力、V0.2.1 升级及便携包启动验收。
- 开发者确认版本完成前不提交 V0.3.1 代码和文档。
- 人工验收使用的候选包不发布；统一版本提交后从确定提交重新构建最终包。
- 推送、创建标签和 GitHub Release 必须再次获得开发者明确确认。

## 选择原因

- 局部点击重试让失败恢复直接对应问题地图块，不会清除其他正常缓存。
- 一次自动重试可以处理偶发读取失败，同时避免后台无限任务和持续资源占用。
- 悬停身份与短时高亮能够确认玩家目标，又不会让地图长期被文字遮挡。
- 缓存统计和实际释放量让破坏性操作的范围可见、结果可核对。
- 保留当前视图的重新加载行为符合已有用户预期，也避免无必要的交互改写。
- 分阶段候选包、统一提交和最终重建兼顾 Rule 18、人工验收与发布产物可追溯性。

## 长期影响

- 地图加载需要维护明确的运行时失败状态和有限重试次数，但失败信息不进入磁盘缓存。
- 玩家身份展示留在界面层，地图瓦片缓存格式保持稳定。
- 缓存模块需要提供统计和删除结果模型，并继续执行严格路径边界保护。
- V0.3.1 的完成标准同时包含功能、稳定性、只读安全、升级和软件包验证。
- 当前决定不建立自动缓存生命周期系统；未来如需引入，必须作为新的重大决策单独确认。
- V0.3.1 完成前不进入后续功能版本。
