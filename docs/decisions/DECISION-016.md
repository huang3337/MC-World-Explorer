# DECISION-016：按资源与模型类型自动适配方块

- **日期**：2026-10-26
- **状态**：开发者已明确提出并授权调整 V0.7.2 方向
- **适用阶段**：V0.7.2 及后续资源适配；不反写已完成 V0.7.1 的验收范围

## 决策内容

完整与非完整方块采用同一资源驱动链路：从选区实际方块状态的 Name/Properties，定位相应 namespace 的 blockstates JSON，选择 variants 或组合 multipart，解析父模型、elements、旋转、UV 和 textures 引用，再自动获取 PNG 并生成网格。

目标是覆盖所有完整/非完整方块的模型表达类型，不建立每种方块名称、木材/石材变种或手工纹理搭配的支持白名单。同类资源结构应自动适用于新方块；具体名称只用于资源 ID、回归样本和有实际问题时的局部兼容修复。不得通过名称后缀猜测几何替代读取模型。

## 备选方案与选择

1. 逐个方块增补名称清单和纹理映射：容易形成重复实现，材质变种与 Mod 扩展成本高，不作为主路径。
2. 按资源引用和模型语义统一解析：复用既有只读资源/图集/网格链路，适配一种表达能力即可覆盖多种方块，采用本方案。

V0.7.1 已实现状态到模型再到纹理的基础解析，但仍有 8 名称白名单、11 个预建状态和按名称筛选属性。V0.7.2 首先移除这三处限制，再扩展模型表达能力；不是重建技术栈或运行 Minecraft。

## 完成口径

台阶、楼梯、火把、栅栏、门、植物等作为不同模型语义的测试样本，不作为有限支持名单。验收以能力与资源覆盖统计为准：已解析、缺资源、未支持表达、非法输入/超限分别报告；不能用少数样本成功冒充全量适配，也不因尚未逐个测试而在入口禁用其他方块。

模型可由常规资源声明表达时自动解析；动态流体、实体/方块实体、内置特殊模型和 Mod 自定义 loader/渲染器等不能从普通 PNG/JSON 独立还原的内容，按渲染类型登记适配任务，保留可见降级原因。全面适配是目标，不在类型适配尚未完成时宣称零例外兼容。

## 对未来 Mod 的影响

资源 ID 的 namespace 原样保留，不限定 minecraft。资源读取边界需允许以后叠加客户端 JAR、Mod JAR 和资源包，并有明确优先级与来源指纹；纯标准 JSON 模型复用通用解析器。现阶段只有客户端源时，Mod 资源缺失应如实报告，不把程序能识别 namespace 当作已找到素材。只读资源，不执行 Mod 代码。

材质的裁剪/半透明、着色等尽量来自资源声明和模型语义，不能只用“图片含透明像素”推断全部渲染规则；确实不在标准模型中声明的语义采用独立类型策略，局部异常集中修复，不散落到逐方块纹理硬编码。

## 特殊渲染类型纳入本期（2026-10-26）

标准客户端审计发现 140 个方块声明没有模型元素，无法单凭普通模型 JSON 还原。开发者已明确选择“接受，本期继续特殊类型适配”：允许在 0.7.2 内增加按渲染类型编写的几何、UV、实体纹理绑定规则，必要时读取方块实体 NBT。标准模型仍自动引用资源，不逐个方块搭配纹理；不执行 Mod/Minecraft 代码。后续不再为已获授权的类型实现重复确认。
