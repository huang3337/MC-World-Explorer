# DECISION-008：V0.5 建立共享解析核心并逐层正式化三维基础

- **状态**：已确认
- **确认日期**：2026-08-03
- **确认人**：项目开发者
- **适用版本**：V0.5 及后续二维与三维开发

## 决策背景

V0.4 在 `experimental.v04` 中验证了完整方块状态解析、简化网格和两个三维渲染后端。该代码以风险验证和后端对比为目的，包含试验参数、测量和双后端职责，不能直接当作正式架构继续扩展。

现有二维 `ParsedChunkSections` 与 V0.4 `VoxelChunkParser` 分别实现了相似的 Palette 和位存储解码。若 V0.5 再建立第三套独立解析逻辑，长期会产生兼容修复重复、二维与三维结果分歧和验证成本上升。另一方面，直接移动整个 V0.4 原型会把实验职责带入正式代码，并削弱 V0.4 证据的可复核性。

该选择会长期影响源码结构、二维与三维数据关系、解析兼容修复位置和后续 V0.6 至 V1.0 的渲染基础，属于重大技术决策。

## 备选方案

### A：逐层正式化并建立共享解析核心

- 新建正式的三维数据、解析、网格和 LWJGL/OpenGL 组件。
- 从 V0.4 选择经过验证的算法迁移并整理接口，不直接移动整个实验目录。
- 二维通过适配层使用共享完整状态解析核心，保持原有行为。
- V0.4 保留为历史验证证据，V0.5 独立验证程序仅组装正式组件。

优点是正式边界清楚、避免长期重复解码，并保留 V0.4 可复核证据。代价是迁移期间新旧实现短暂并行，且二维适配必须进行完整回归验证。

### B：按 V0.5 设计完全重写

- V0.4 只作为行为参考，正式基础全部重新实现。
- 可以从空白结构开始，但会重复已经完成的解析和边界验证，也更容易重新引入已修复问题。

### C：直接重构 V0.4 原型

- 移动或改名 V0.4 类，使其成为正式包，再补充多区块和分层网格能力。
- 初期改动较快，但实验参数、测量、JavaFX 对照后端和正式职责容易混杂，并会改变历史验证代码。

## 最终选择

选择 **A：逐层正式化并建立共享解析核心**。

- 正式代码位于 `com.mcworldexplorer.voxel` 及其数据、读取、网格和 LWJGL 渲染子包。
- V0.5 验证入口位于 `com.mcworldexplorer.experimental.v05`，只负责参数、组装、窗口、报告和截图。
- `com.mcworldexplorer.experimental.v04` 保持原样，不继续添加正式三维功能。
- 二维适配层继续提供现有方块名称和采样契约，迁移不得改变二维地图行为或缓存格式。
- V0.5 不接入正式主界面，不发布正式用户软件包。

## 选择原因

- 一套共享 Palette 解码逻辑可以让兼容修复同时服务二维和三维，降低长期分歧风险。
- 完整状态模型能够满足后续纹理、模型和渲染层需求，同时允许二维只消费方块名称。
- 逐层迁移可以复用 V0.4 已验证算法，又能重新建立清晰的正式职责边界。
- 保留 V0.4 原型可以继续复核后端选择、解析行为和历史性能证据。
- 独立 V0.5 验证入口符合内部基础阶段的定位，不会提前形成用户界面兼容承诺。

## 长期影响

- 二维与三维共享底层完整状态解码，未来解析格式修复原则上只在正式核心实现一次。
- 二维适配层必须保持 V0.3.1 稳定基线；任何迁移都需要完整二维回归和固定样本对比。
- 正式数据与网格模型不能依赖 JavaFX 或 LWJGL，避免数据层被单一后端锁定。
- 正式 LWJGL 组件必须保持显式线程、上下文和 GPU 资源生命周期。
- V0.4 代码暂时保留；未来归档或删除仍需单独影响审查和开发者确认。
- 本决策不自动授权 V0.5 完成、提交、推送、打包或发布，这些门禁继续分别执行。
